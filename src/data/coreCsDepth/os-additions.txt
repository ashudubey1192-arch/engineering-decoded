@program-vs-process
Code is a recipe; a process is an execution|An executable file contains instructions and static metadata. A process combines those instructions with a current instruction pointer, registers, address mappings, credentials, and references to open resources. Starting the same executable twice creates two executions with independent lifetimes. Their read-only code pages can still share physical storage without making their mutable application variables shared.
Example: two copies of a counter|Launch two programs whose variable starts at zero. Incrementing the first program's variable does not increment the second, even when a debugger displays the same virtual address in both. Each address is interpreted in its own address space. Explicit shared memory or another IPC mechanism is necessary to coordinate their counters; identical program text is not a communication channel.
@the-process-control-block
The kernel's execution record|The textbook process control block groups the information needed to manage execution: identity, state, saved registers, scheduling metadata, accounting, and references to memory and files. Real kernels distribute these responsibilities among linked structures. A task record should therefore be understood as an entry point into an object graph, not as a copy of every byte the process owns.
Example: suspending and resuming a worker|A worker blocks while reading a socket. The kernel records where execution can resume and attaches the task to an appropriate wait mechanism. Its memory mappings and open socket remain alive. When data arrives, the task becomes runnable; only after a scheduler selects it do the saved context and kernel continuation actually resume. Waking and running are separate events.
@process-states
Runnable, running, and blocked|Running means a CPU is executing the task now. Runnable means the task could execute but is waiting for CPU service. Blocked means an event, such as data availability or a lock release, must occur first. A timer may move a running task back to the runnable queue; an I/O completion moves a blocked task to runnable, not directly onto a CPU.
Example: latency with an idle CPU|A request spends 2 ms computing, 40 ms waiting for storage, and 3 ms runnable behind other work. Its elapsed time is 45 ms even though it uses only 2 ms of CPU. More cores might reduce the 3 ms queue delay but cannot remove the 40 ms device wait. Diagnose state durations before selecting a performance fix.
@fork-exec-wait-exit
Separate creation, replacement, and collection|fork creates a child execution; exec replaces a program image; wait collects a child's termination status; exit ends execution. Treating these as one operation hides important failure paths. The child must handle a failed exec, and the parent must eventually collect children it is responsible for. A shell also arranges descriptor redirection before starting the requested program.
Example: why output can appear twice|Buffered output created before a fork can exist in both processes' user-space buffers afterward. If each process later flushes that buffer, the same text can be emitted twice even though the original print statement ran once. Flush deliberately before creation when appropriate, and use the correct child failure path after exec fails. Also close unused pipe ends so readers can observe end-of-file.
@clone-and-what-fork-shares
Sharing is a set of choices|Linux task creation can select which resources are shared, such as address space, descriptor table, and signal-handler configuration. Thread creation uses a coordinated combination of these choices rather than merely changing a task's name. Sharing an address space lets tasks see the same allocations, but each running thread still needs its own execution context and stack discipline.
Example: descriptor table versus open object|Two tasks can have separate descriptor tables whose entries reference the same open file description, or they can share the descriptor table itself. In the first case closing one entry does not remove the other's entry, although file offsets may be shared. In the second, table mutations are visible to both. Always identify which layer is shared before predicting behavior.
@zombies-and-orphans
Termination does not finish the parent's bookkeeping|A zombie has stopped executing and released ordinary execution resources, but retains enough information for its parent to collect an exit status. It is not consuming CPU in an endless loop. An orphan is a child whose parent has exited; it may still be running. Adoption and reaping behavior depends on the process hierarchy, including subreapers and PID namespaces.
Example: a supervisor that never waits|A supervisor launches a short-lived child every second but never collects results. Child execution ends normally while retained termination records accumulate. Killing an already terminated child cannot solve this leak. The supervisor must reap children and handle bursts of exits correctly, rather than assuming one signal corresponds to exactly one terminated child. Design shutdown and error paths to reap as well.
@context-switching
Direct work and indirect disruption|A switch preserves one execution context and restores another. Depending on the tasks and architecture, it may also change memory-translation context and other CPU state. Direct register bookkeeping is only part of the cost. The incoming task may need instructions and data that displaced the previous task's useful cache working set.
Example: more workers can reduce throughput|Suppose eight CPU-heavy workers compete on two available CPUs. Adding another hundred workers does not create CPU capacity. It can increase runnable waiting, scheduler work, and cache churn. Measure completions, runnable delay, and switches together. A high switch count can also reflect productive I/O concurrency, so the counter alone does not prove a problem or justify reducing concurrency.
@signals
Notification with restricted execution context|A signal can request termination, report a fault, or notify a process of an event. Disposition determines whether the default action, a handler, or ignoring applies; masks control delivery to threads. Handlers interrupt normal control flow, so calling arbitrary library functions from them can deadlock or corrupt state. Use the platform's async-signal-safe operations or defer work to normal execution.
Example: graceful shutdown|On a termination request, record a shutdown flag or notify the main event loop through a suitable mechanism. Stop accepting new work, finish bounded in-flight operations, and close resources in ordinary code. Do not perform complex logging, allocation, and mutex-heavy cleanup inside the handler. Standard signals may coalesce, so use durable state rather than treating deliveries as a reliable event count.
@process-groups-sessions-and-jobs
Organizing a terminal workload|A process group collects related processes, often the members of a shell pipeline. A session groups process groups and may own a controlling terminal. The foreground process group receives terminal-generated signals. These relationships are independent of whether a process is currently scheduled, and they are more expressive than assuming every child should receive every signal sent to its parent.
Example: stopping a pipeline|For a command pipeline, the shell arranges the participating commands into a job. Pressing the terminal interrupt key targets the foreground group, allowing all pipeline members to react. A background job is a different group, not a lower-priority CPU class. A robust shell tracks group state and waits for all relevant children before declaring a job fully completed.
@why-scheduling-exists
CPU service is a shared resource|Runnable tasks compete for a finite number of execution slots. Scheduling selects who runs, for how long, and on which CPU. The objective depends on workload: interactive responsiveness, batch throughput, fairness, or deadline compliance. A policy that maximizes total work can still produce unacceptable pauses for a user-facing task, so there is no universal best ordering.
Example: overlap computation with waiting|Task A computes for 3 ms and blocks for 20 ms; task B has 10 ms of independent CPU work. Scheduling B while A waits uses time that would otherwise be idle. When A becomes ready, preemption policy determines its response delay. This overlap improves utilization on one CPU without allowing the two instruction streams to execute simultaneously.
@scheduling-metrics
Measure the right interval|Turnaround is completion time minus arrival time. Response time is first execution time minus arrival time. Waiting time measures runnable time without CPU service; blocked time is separate. Throughput counts completions per interval, while utilization measures occupied capacity. Means hide outliers, so include latency distributions and distinguish a process-level CPU metric from the user's end-to-end request latency.
Worked calculation|A CPU-only job arrives at time 2, first runs at 5, uses 4 time units, and finishes at 11 after preemption. Its turnaround is 9, response is 3, and total runnable waiting is 5. If it instead includes 2 units blocked on I/O, waiting becomes 3. Subtracting only CPU time from turnaround is valid only when other states are accounted for.
@fcfs-sjf-and-srtf
Ordering and preemption|First-come, first-served runs jobs in arrival order without preemption. Shortest-job-first chooses the smallest available CPU burst but needs a prediction of that duration. Shortest-remaining-time-first can preempt when a newly available job has less work remaining. Short-job policies can reduce average waiting while making a long job wait repeatedly under a stream of short arrivals.
Worked schedule|Let A and B arrive at time 0 with bursts of 8 and 2, and C arrive at time 1 with burst 1. FCFS with A first completes A at 8, B at 10, and C at 11. Nonpreemptive SJF starts B, then C, then A, completing at 2, 3, and 11. Record the arrival assumptions and tie-break rule; otherwise two apparently conflicting schedules may both be valid.
@round-robin
The quantum controls a trade-off|Round robin rotates runnable tasks after a bounded quantum. A short quantum improves opportunities to respond but creates more switch overhead. A very long quantum approaches first-come behavior for short bursts. Blocking tasks normally leave the runnable rotation until their event completes. Fair turns are not necessarily equal useful work when tasks have different cache behavior or CPU requirements.
Worked schedule|With all jobs arriving at zero, bursts A=5, B=3, C=1 and quantum 2 produce A:0–2, B:2–4, C:4–5, A:5–7, B:7–8, A:8–9, ignoring switch cost. Completion times are 9, 8, and 5. Change the quantum to 1 and recompute response and completion times. Then insert a fixed switch cost to see why smaller slices are not free.
@priority-scheduling-and-aging
Urgency and starvation|A priority scheduler favors higher-ranked runnable tasks. Static priorities are easy to reason about but can indefinitely delay low-priority work if higher-priority demand never stops. Aging increases waiting tasks' effective priority over time, providing a path toward service. The implementation must define whether aging resets after execution and how equal-priority tasks share CPU time.
Example: maintenance behind requests|A server gives interactive requests priority over cleanup. During sustained traffic the cleanup never runs, so temporary files accumulate until requests fail too. Aging or a reserved service budget can keep background work progressing. Do not confuse this starvation problem with priority inversion: inversion involves a high-priority task waiting for a resource held by lower-priority work.
@multilevel-queues-and-mlfq
Fixed classification versus feedback|Multilevel queues divide work into classes with different scheduling rules. A feedback queue additionally moves tasks according to observed behavior. Tasks using a full quantum may move to a lower queue, while short interactive bursts can remain responsive. Periodic priority boosts help prevent starvation. Actual rules must account for total CPU use so tasks cannot game classification by yielding just before expiration.
Example: interactive and CPU-heavy jobs|A text editor frequently waits for input, whereas a compiler consumes long CPU bursts. A feedback policy can give the editor quick service without making the compiler permanently ineligible. Track cumulative service across voluntary yields: otherwise a compute task can pretend to be interactive. Compare queue transitions over several bursts, not just the first scheduling decision.
@multiprocessor-scheduling
Placement affects locality|Multiple CPUs introduce a placement decision in addition to ordering. Per-CPU queues reduce shared-queue contention, but balancing may move tasks between CPUs. Migration can lose cache warmth and change memory locality. Affinity narrows eligible CPUs; it does not guarantee exclusive access. Simultaneous multithreading also means two logical CPUs can share important physical-core resources.
Example: an uneven machine|Four workers are pinned to one CPU while three others are idle. Aggregate utilization looks low even though the workers experience a saturated run queue. Relaxing affinity may help, but moving a memory-heavy task far from its NUMA-local pages can add access latency. Inspect allowed CPUs, per-CPU demand, and memory placement before treating balancing as a purely numerical problem.
@real-time-scheduling
A deadline is a correctness constraint|Real-time scheduling reasons about completing work before deadlines, not merely running quickly on average. Hard deadlines cannot tolerate misses; soft deadlines permit degraded value. Fixed-priority and earliest-deadline policies require assumptions about execution cost, periods, blocking, and preemption. Admission control prevents accepting a workload whose required service exceeds available capacity under the model.
Worked utilization check|For independent periodic tasks with execution/period pairs 1/5 and 2/10, utilization is 0.2+0.2=0.4. That leaves capacity in a simplified single-CPU model, but does not prove every real system will meet deadlines: interrupts, locks, nonpreemptible work, and underestimated execution cost matter. State assumptions before applying a utilization bound, and measure worst-case behavior rather than substituting average runtime.
@linux-scheduling-classes
Policy names express different contracts|Linux distinguishes ordinary fair scheduling from real-time policies such as FIFO and round robin and from deadline scheduling. A real-time task can outrank ordinary work even when ordinary tasks have waited a long time. Nice values adjust relative weighting within the appropriate ordinary policy; they do not turn a process into a deadline-guaranteed task.
Example: a busy high-priority thread|A high-priority FIFO thread that never blocks can prevent lower-priority work from progressing on an eligible CPU, subject to configured controls. That includes the work needed to service the application itself. Test scheduling changes in a bounded environment and verify runtime limits. Kernel configuration, available policies, privilege checks, and container limits influence what is actually permitted.
@fair-scheduling-cfs-to-eevdf
Virtual service and eligibility|Fair scheduling tracks service relative to a task's weight rather than assigning every task identical elapsed slices. CFS organized decisions around virtual runtime. EEVDF adds eligibility based on whether a task is owed service and selects an eligible task with an early virtual deadline. The distinction allows responsiveness to be considered while retaining a model of fair long-term allocation.
Reason through a weighted example|If two continuously runnable tasks have weights in a 2:1 ratio on one CPU, their long-run service target is roughly two thirds and one third, not equal halves. A newly waking task also needs a fair treatment of prior service. A short slice can improve responsiveness without granting unlimited extra CPU. Verify the running kernel's implementation before assuming a textbook CFS trace describes current behavior.
@what-a-thread-is-to-the-kernel
Execution identity and shared ownership|A kernel-scheduled thread has registers, a stack, scheduling state, and a thread identity. Threads in one process usually share the address space and many resource references. This sharing is why one thread can pass an allocation to another, but it is also why an invalid write can damage the entire application. Scheduling independence does not imply memory isolation.
Example: a blocked worker|When one thread waits for a socket, another kernel thread in the same process may execute. They can simultaneously access shared heap objects on separate CPUs. A stack variable is not automatically inaccessible to other threads if its address escapes; its lifetime and synchronization still matter. Distinguish the convention of private stack ownership from hardware-enforced address-space protection.
@processes-vs-threads
Isolation changes the failure boundary|Processes provide separate address spaces by default, which makes accidental cross-process memory corruption harder. Threads make sharing cheap but put correctness responsibility on synchronization and ownership rules. IPC between processes introduces serialization, copying, or shared-memory coordination. Compare recovery needs and data-sharing patterns rather than choosing solely from the slogan that threads are lighter.
Example: plugin execution|An untrusted or unstable plugin inside a thread can corrupt the host heap or terminate the process. Running it in a separate process creates a stronger crash boundary and permits restart, but the protocol must handle partial messages, deadlines, and plugin failure. Shared memory can improve throughput while reintroducing some shared-state complexity; it does not erase the process boundary's other benefits.
@user-and-kernel-threads
Who makes the scheduling decision?|A runtime can schedule many logical tasks onto fewer kernel threads. The kernel sees runnable carrier threads, while the runtime sees its own task queues. This reduces per-task overhead but makes blocking behavior important: a blocking call can occupy a carrier unless the runtime parks, replaces, or otherwise compensates for it. Mapping models vary by runtime and operation.
Example: one carrier, many tasks|A cooperative runtime has one kernel thread and a thousand logical tasks. If one task performs long CPU work without yielding, the other tasks cannot progress even when the OS would happily schedule another kernel thread. Async I/O helps with waiting, not CPU computation. Offload bounded CPU work or provide more carriers according to the runtime's model.
@thread-creation-and-teardown
Creation is only the start of a lifecycle|A new thread needs a stack, runtime bookkeeping, and a start routine with valid arguments. The parent must not free or reuse those arguments before the child finishes reading them. Joinable threads require joining to collect completion and release relevant resources; detached threads need another reliable ownership strategy. Cancellation must not abandon locked resources or half-updated invariants.
Example: a loop-variable bug|A loop starts workers and gives each the address of the same changing loop variable. Workers can observe later values rather than their intended index. Give each worker stable per-worker input and keep it alive until the worker no longer needs it. During shutdown, stop new submissions, signal existing workers, and join them before destroying their shared queue or synchronization objects.
@what-a-context-switch-costs
Costs depend on what changes|Switching between threads sharing an address space may avoid some address-space changes, but still requires execution-state bookkeeping and scheduler work. Cache, translation, and branch-prediction effects can dominate the direct path. A task with a large working set may recover slowly after displacement. There is no single nanosecond constant that accurately describes every switch on every machine.
Example: interpreting a benchmark|A ping-pong test between two threads includes synchronization, wake-up, scheduling, and communication costs, not just saving registers. Place threads on the same CPU and on different CPUs to expose different paths, but record affinity and workload. Use the result to compare a specific design under stated conditions; do not present it as the universal hardware cost of a context switch.
@thread-pools-and-sizing
Bound work, not only workers|A pool amortizes thread creation and limits simultaneously executing tasks. A queue separates admission from execution; if it is unbounded, the pool can still consume unlimited memory and build extreme latency. Choose queue limits, rejection behavior, timeouts, and shutdown rules alongside worker count. Separate workloads that can block each other, such as CPU jobs and slow external calls.
Worked sizing estimate|With four usable CPUs, a task using 5 ms CPU and waiting 15 ms has a rough saturation estimate of 4×(1+15/5)=16 workers, assuming independent waits and no other bottleneck. This is a starting hypothesis, not a guarantee. A database allowing only six concurrent queries or a strict memory limit may require fewer. Measure throughput and tail latency as concurrency changes.
@runtime-threading-models
Language tasks do not all mean OS threads|A language may expose native threads, virtual threads, coroutines, or async tasks. These abstractions differ in scheduling, suspension, cancellation, and interaction with blocking native calls. Runtime garbage collection and safepoints can also affect progress. Understand the particular runtime version and APIs instead of inferring kernel behavior from an object named Thread or Task.
Example: asynchronous versus parallel|An async web handler can suspend while waiting for a response without occupying a dedicated thread for the entire wait. That does not make a CPU-heavy loop parallel or preemptible by other logical tasks on the same event loop. Use a bounded executor for expensive computation where appropriate, and propagate cancellation and deadlines so abandoned requests do not keep consuming capacity.
@race-conditions-and-atomicity
An operation can contain several visible steps|Incrementing a shared counter conceptually reads, computes, and writes. Two threads can both read 10, both compute 11, and both write 11, losing one increment. Atomic read-modify-write operations make that particular update indivisible, but do not automatically protect a multi-variable invariant. In languages such as C and C++, unsynchronized data races can invalidate ordinary reasoning through undefined behavior.
Example: transferring a balance|Moving 10 units from account A to B must preserve the sum and avoid overdraft. Making each balance atomic does not make the combined check-and-transfer atomic. Use a lock covering the invariant, a correct transaction, or a carefully designed compare-and-swap protocol. Specify a consistent lock order when multiple accounts are involved, and test interleavings around validation as well as updates.
@memory-ordering-and-false-sharing
Visibility, ordering, and cache ownership|An atomic flag can coordinate publication only when its ordering establishes the required relationship with the published data. Release/acquire synchronization is one common pattern; a relaxed atomic alone does not publish unrelated writes. False sharing is different: independent variables occupy the same cache line and cause coherence traffic even though the program has no logical data dependency between them.
Example: two per-thread counters|Two workers repeatedly update separate counters stored next to each other. If both lie in one cache line, ownership can bounce between cores on each write. Padding or separating hot data may improve throughput, at the cost of memory and cache capacity. First verify the access pattern and actual contention; padding every object can make locality worse rather than better.
@mutexes-semaphores-and-condition-variables
Different primitives protect different facts|A mutex gives one owner exclusive access to an invariant. A semaphore counts available permits and can allow several participants. A condition variable allows waiting for a predicate protected by a mutex; it is not a queue of durable notifications. Waiting releases the mutex atomically with entering the wait protocol and reacquires it before the caller checks shared state again.
Example: a bounded queue|The consumer locks the queue and waits in a loop while it is empty. The producer inserts an item under the same lock and signals availability. The consumer rechecks because another consumer may win the item or the wake-up may be spurious. A signal sent before a waiter exists is harmless only if the actual predicate, such as a nonempty queue, remains recorded in shared state.
@how-blocking-works
The lost-wake-up problem|A naive waiter checks that no work exists, then goes to sleep. If a producer publishes work and signals between those two actions, the waiter can sleep forever. Correct wait protocols couple condition checking with registration for notification. Linux futex-based designs combine an atomic user-space state with kernel-assisted waiting when the expected state still holds.
Example: uncontended and contended locking|On an uncontended fast path, an atomic update can acquire a mutex without a kernel wait. On contention, the implementation records waiting and parks through an appropriate kernel mechanism. Unlocking changes the state and may wake a waiter. Waking does not transfer CPU execution immediately and may not transfer ownership directly; the contender must follow the mutex's acquisition protocol.
@spinlocks-and-interrupt-context
Spinning consumes the CPU while waiting|A spinlock repeatedly checks for ownership instead of sleeping. It is suitable only when the expected wait is short and the holder can make progress. Interrupt and preemption constraints matter: an interrupt handler that spins on a lock held by the interrupted context on the same CPU can deadlock. Kernel lock variants encode these context-specific requirements.
Example: choosing the wrong wait|If a critical section performs disk I/O, a spinning contender can waste a full CPU while storage takes milliseconds. A sleeping lock is usually appropriate in a context allowed to sleep. Conversely, a context that must not schedule cannot simply substitute a mutex. Keep critical sections short, document lock context, and reason about who can interrupt whom, not just how many threads exist.
@deadlock
Four conditions form a cycle|Deadlock needs mutual exclusion, holding resources while requesting more, lack of forced resource reclamation, and a circular dependency. Prevention breaks one of these conditions; avoidance reasons about safe allocation; detection finds cycles or equivalent evidence after they form. A timeout can limit waiting but does not automatically undo partially completed work or restore the application's invariant.
Worked lock-order example|Thread A holds lock X and waits for Y; thread B holds Y and waits for X. Neither can reach its unlock. Requiring every path to acquire X before Y removes that particular cycle. Ordering must include callbacks and error paths too. If acquiring many resources dynamically, sort by a stable identity or use a protocol that releases and retries without leaving partial updates behind.
@starvation-livelock-and-priority-inversion
Progress failures have different mechanisms|Starvation means a task never receives the resource it needs while others progress. Livelock means tasks remain active but repeatedly undo or avoid each other without useful completion. Priority inversion means urgent work depends on a resource held by lower-priority work, potentially delayed by intermediate-priority tasks. Different mechanisms require different remedies; adding a timeout does not identify the cause.
Example: inversion across three tasks|Low-priority L holds a mutex. High-priority H blocks on it. Medium-priority M remains runnable and prevents L from finishing, indirectly delaying H. Priority inheritance temporarily raises the relevant holder's priority so it can release the lock. It does not eliminate long critical sections or arbitrary dependency chains. For livelock in symmetric retries, randomized backoff may help where priority inheritance cannot.
